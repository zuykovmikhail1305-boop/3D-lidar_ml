Семь **ROS 2 бэгов** (`rosbag2` версии 5, хранилище sqlite3). В каждом ровно один
топик — поток свипов 128-лучевого лидара. Ни одометрии, ни TF, ни камер, ни разметки.

Две поставки различаются по раскладке. Первая — шесть независимых записей, у каждой
свой каталог с одним `.db3`. Вторая — **один бэг, разрезанный rosbag2 на 221 часть**;
порядок частей задан в `metadata.yaml`, и отдельная часть сама по себе неполна.
`open_bag()` разбирает обе раскладки одинаково и отдаёт сплошную нумерацию кадров.

### Топик и формат сообщения

Топик называется `/lidar_points` в шести бэгах и
`/sensing/lidar/hesai128/pointcloud` в `doubleT_obstacle`. Тип —
`sensor_msgs/msg/PointCloud2`, сериализация CDR.

Каждое сообщение — неорганизованное облако (`height = 1`), `point_step = 26` байт:

| поле | смещение | тип | смысл |
|---|---:|---|---|
| `x` | 0 | float32 | поперёк тоннеля, +x вправо [м] |
| `y` | 4 | float32 | вдоль тоннеля, **вперёд — это −y** [м] |
| `z` | 8 | float32 | по вертикали, +z вверх [м] |
| `intensity` | 12 | float32 | отражательная способность, 0–255 |
| `ring` | 16 | uint16 | номер луча, 0–127 |
| `timestamp` | 18 | float64 | абсолютное время точки [с] |

Обратите внимание: структура **упакована без выравнивания по 8 байтам** —
`timestamp` стоит на смещении 18, поэтому наивный вью `float64` промахнётся.
В `rosbag_pc2.py` для этого собирается явный numpy-dtype с `itemsize = 26`.

### Геометрия сенсора (выведена из данных, в бэгах не задокументирована)

- 128 колец в диапазоне элевации **+14.40°…−25.12°** — это Hesai Pandar/OT-128.
- Порядок точек **column-major**: `index = номер_колонки * 128 + ring`. Поэтому
  `array.reshape(-1, 128).T` даёт корректный range-image вида `(кольцо, азимут)`.
- Азимутальный охват различается по бэгам:
  - шесть бэгов, включая `new_data`: 2400 колонок в **секторе 100° вперёд** (−140°…−40°, центр на −90°,
    то есть по направлению движения −y);
  - `doubleT_obstacle`: 7200 колонок на **360°**, с перекрытым сектором сзади.
- «Нет отражения» кодируется **точным нулём (0,0,0)**, а не NaN. Реальные отражения
  есть в 38–62 % слотов, остальное — небо и поглощённые лучи. Фильтровать нужно по
  `|x|+|y|+|z| > 0`, проверка `isfinite` здесь ничего не даёт.
- Дальности — от ~1.9 м до ~209 м (дальний конец тоннеля).

### Что в сценариях

Названия расшифровываются как проезды по инфраструктуре тоннеля. Подтверждено
по сечениям:

- `roundT` — круглый ствол, радиус ≈ 2.4–3.2 м.
- `squareT` — прямоугольное сечение, ширина ≈ 4.5 м.
- `doubleT` — двухпутный прямоугольный тоннель, ≈ 9.5 м в ширину и 5 м в высоту;
  сенсор смещён от оси, ближе к левой стене.
- `pressureGate` — ниша гермозатвора: на накопленном профиле радиус расширяется
  с ~3 м до ~5.2 м на дистанции от 10 до 16 м.
- `platform` / `switch` / `obstacle` — край платформы, ответвление пути
  (боковой проход виден около x ≈ +9 м) и поставленное препятствие.

Имена файлов читаются как последовательность участков одного проезда, например
`roundT_squareT_pressureGate_squareT` = круглый ствол → прямоугольный →
гермозатвор → прямоугольный.

### Оговорки

- **Позы нет.** В бэгах отсутствуют топики `/tf`, `/odom` и IMU. Смещение между
  кадрами мало (медианное изменение дальности 0.02–0.2 м за несколько секунд), а
  тоннели самоподобны, поэтому простой одномерной корреляцией сдвиг не
  восстанавливается — нужна регистрация (ICP/NDT) или пакет лидарной одометрии.
  Поэтому команда `map` накладывает кадры **в системе координат сенсора**.
- Отметки времени — порядка `946 69x xxx` с (2000 год), то есть симулированные или
  переигранные часы, тогда как собственное время записи бэга — 2026 год. Поле
  `timestamp` стоит использовать только для упорядочивания.
- Номинальная частота — 10 Гц, но записи не идеальны: в первой поставке пропуски
  до 1.1 с, в `new_data` — 34 разрыва длиннее 0.3 с, максимальный 7.1 с.

## Использование

У всех команд есть флаги `--root` (по умолчанию путь выше), `--mode light|dark`
и `--out`. **Флаги указываются после подкоманды.** Картинки складываются в `./out/`
относительно текущего каталога.

Сводка по датасету: таблица в консоль плюс рисунок с числом кадров,
длительностями и таймлайном записи.

```bash
python visualize.py overview
```

Один свип в четырёх проекциях — вид сверху, вид сбоку, поперечное сечение
тоннеля и range-image.

```bash
python visualize.py frame roundT_doubleT --index 120
```

Дальность, интенсивность и высота в виде изображений `(128 × азимут)` — это
естественный формат для всего, что скармливается свёрточным сетям.

```bash
python visualize.py rangeimage roundT_pressureGate_roundT -i 60
```

Наложение множества кадров в одну карту плотности. Третья панель разворачивает
радиус тоннеля вдоль проезда — именно на ней видны гермозатворы, ниши и платформы.

```bash
python visualize.py map roundT_pressureGate_roundT --stride 8
```

Анимация проезда: вид сверху рядом с живым поперечным сечением.

```bash
python visualize.py animate doubleT_platform --stride 6 --limit 40 --fps 8
```

Весь проезд одной картинкой — для длинных записей вроде `new_data`. Развёртка
обделки по углу вокруг оси тоннеля, сложенная по времени: каждый тип сечения
читается своей полосой, а гермозатворы, камеры и ответвления — разрывами в ней.
Скан кэшируется в `.npz`, повторный запуск рисует мгновенно.

```bash
python visualize.py timeline new_data --stride 10
```

Выгрузка кадра для CloudCompare / MeshLab / Open3D.

```bash
python visualize.py export roundT_doubleT -i 0 --format ply
```

## Как пользоваться ридером напрямую

```python
from rosbag_pc2 import open_bag, xyz

bag = BagReader(r'D:\hack\extracted\for_hackathon\roundT_doubleT\roundT_doubleT_0.db3')
print(len(bag), 'кадров')

meta, points = bag.read(120)          # points — структурированный numpy-массив
cloud = xyz(points)                   # (N, 3) float32, пустые отсчёты убраны
print(meta['frame_id'], cloud.shape, points['intensity'].max())

for i, (meta, points) in bag.iter_messages(step=10):
    ...
```

Ридер держит в памяти только индекс id/timestamp и достаёт сообщения по одному по
первичному ключу. Составной бэг индексируется один раз при открытии: 221 часть,
11 271 кадр — около 2 секунд, блобы точек при этом не читаются. Дальше открытыми
держатся последние несколько частей, так что чтение кадра стоит примерно 8 МБ
независимо от размера бэга.
